↔ Spotify Mirror

Point it at any Spotify playlist, album, or artist. It fetches metadata, finds each track on YouTube, downloads, converts to MP3, and writes history to the database.

Core pipeline

From playlist link to tagged local library

The middle of this product is not a generic downloader. It is a controlled media pipeline that resolves a source, enriches it with metadata, downloads the right asset, and records the job state so the whole flow stays repeatable.

  • Spotify links become structured track batches before any download starts.
  • YouTube matching and audio conversion happen under bounded concurrency.
  • Every finished file is tagged, stored, and written back to PostgreSQL.

01

Parse source

Accept a Spotify URL or URI and classify it as a playlist, album, or artist collection before any job fan-out begins.

02

Fetch metadata

Pull titles, artists, and duration from Spotify using OAuth first, with sp_dc available when editorial access needs a pragmatic fallback.

03

Match on YouTube

Search YouTube track by track to find the strongest audio candidate, with YouTube Music lookup used when playlist context needs a second pass.

04

Download and convert

yt-dlp pulls the stream, FFmpeg converts it to MP3, and semaphore caps keep large playlist jobs from flooding the machine.

05

Tag and persist

mutagen writes ID3 tags, then the file path, history, and job state are committed to PostgreSQL so the local library remains queryable.

Why no npm?

The frontend is intentionally zero-toolchain. Static HTML, CSS, and JS served directly by FastAPI. No bundler, no transpiler, no node_modules. It's a deliberate constraint that keeps the project deployable and understandable without a separate frontend environment.

Why two Spotify auth strategies?

The Spotify API restricts access to editorial playlists behind OAuth. The sp_dc cookie flow was added as a pragmatic fallback for cases where OAuth isn't the right fit. Supporting both means the tool works in more real-world situations.

Why semaphore-based concurrency?

Unbounded parallel downloads will saturate disk I/O and network quickly. A configurable semaphore cap keeps the system stable under large playlist jobs without needing a full job queue.

Why PostgreSQL for a local tool?

Download history, job state, and mirror records need to survive restarts and be queryable. A flat file would have worked for simple history, but PostgreSQL gives proper job tracking, progress upserts, and storage stats with almost no overhead for a local setup.
