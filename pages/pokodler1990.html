The problem it solves

FastAPI yt-dlp PostgreSQL Spotify API Python 3.11+ Vanilla JS FFmpeg mutagen

Downloading music from the internet is a solved problem — until you need it to be repeatable, organised, and auditable. Most tools give you a file. PokoDler 1990 gives you a pipeline: structured folders, ID3 metadata, job history, and a Spotify-to-local-library mirror that remembers what it has already done.

  • Any YouTube URL or playlist becomes a tagged local audio or video file in one command.
  • Any Spotify playlist, album, or artist is resolved, matched on YouTube, downloaded, and written to PostgreSQL.
  • Download history survives restarts and is queryable — no re-downloading what you already own.
  • Concurrency is bounded by a semaphore so large batch jobs never saturate the machine.

Three operating modes

Every workflow in PokoDler maps to one of three clearly separated modes. They share the same pipeline core but differ in source, fan-out strategy, and job scope.

⬇ Mode 01 · Single Download

One URL, one file

Paste any YouTube URL. Choose audio or video. The file lands in an organised local folder, ID3-tagged and immediately playable.

  • Audio extracts to MP3 via FFmpeg at configurable quality.
  • Video saved to an MP4 at best available resolution.
  • Title, artist, and duration tags written automatically using mutagen.
  • Job recorded to downloaded_songs table for history.

⊞ Mode 02 · Playlist Batch

Full playlist, bounded concurrency

Point it at a YouTube playlist and walk away. Concurrent jobs run under a semaphore limit — no resource hammering on large collections.

  • Downloads into a timestamped, sanitised folder per playlist.
  • Semaphore cap prevents I/O and network saturation.
  • Each item tagged and logged independently — partial runs are safe to resume.
  • Progress surface available via FastAPI status endpoint.

↔ Mode 03 · Spotify Mirror

Spotify library → local MP3

The flagship mode: resolve a Spotify source, match every track on YouTube, download and convert, write history. The full pipeline in one flow.

  • Accepts playlist, album, or artist links as input.
  • OAuth-first with sp_dc cookie fallback for editorial playlists.
  • YouTube Music lookup as a second-pass matcher for better audio candidates.
  • Mirror history persisted to spotify_downloads — already-owned tracks are skipped.

Core pipeline · Spotify Mirror

From playlist link to tagged local library

The pipeline resolves a source, enriches it with metadata, downloads the right asset, and records the job state — making the whole flow repeatable and auditable.

Step 01 · Input

Parse source

Accept a Spotify URL or URI and classify it as a playlist, album, or artist collection before any job fan-out begins. The type determines the downstream fetch strategy and folder structure.

  • Playlist: Fetches ordered tracks, preserves sequence.
  • Album: Groups by release, tags with album metadata.
  • Artist: Pulls top tracks or full discography depending on config.

Step 02 · Enrichment

Fetch Spotify metadata

Pull titles, artists, album art, and duration from the Spotify API using OAuth first-party access, with the sp_dc cookie available as a pragmatic fallback when editorial playlist access needs a second path.

  • OAuth token managed and refreshed automatically.
  • sp_dc fallback unlocks editorial and regional-restricted content.
  • Duration data used downstream to improve YouTube match scoring.

Step 03 · Matching

Match on YouTube

Search YouTube track by track to find the strongest audio candidate. YouTube Music lookup is used as a second pass when the standard search returns ambiguous results or live/cover versions.

  • Candidate scored against duration and title similarity thresholds.
  • YouTube Music API consulted for playlist-context-aware matches.
  • Failed matches logged with reason — never silently skipped.

Step 04 · Conversion

Download and convert

yt-dlp pulls the audio stream and FFmpeg converts it to MP3 at the configured bitrate. A semaphore cap keeps large playlist jobs stable without needing a full job queue infrastructure.

  • Semaphore limit configurable per run — defaults to 3 concurrent workers.
  • FFmpeg postprocessor handles format conversion and normalization.
  • Output folder named and sanitised deterministically from track metadata.

Step 05 · Persistence

Tag and persist

mutagen writes ID3 tags — title, artist, album, and duration — to the finished MP3. The file path, mirror history, and job state are then committed to PostgreSQL so the local library stays queryable and restartable.

  • ID3v2 tags written for compatibility with all major media players.
  • Three tables: downloaded_songs, spotify_downloads, jobs.
  • Schema auto-created on first startup — no migration tooling needed.
  • Upsert strategy: re-running a mirror skips already-downloaded tracks.

Architecture

Layered and separated by concern

🖥

Frontend

Static HTML / CSS / Vanilla JS. Zero build toolchain, zero npm. Served directly by FastAPI's StaticFiles mount — deployable without a separate frontend environment.

⚡

API Layer

FastAPI routes split across four domains: /downloads, /spotify, /files, and /stats. Clean HTTP boundary with async request handling throughout.

⚙

Service Layer

Download orchestration, Spotify resolution logic, and database access live as independent service modules. Each can be tested and modified without touching the API routes.

🗄

Persistence

PostgreSQL via psycopg2. Three tables handle all state: downloaded_songs, spotify_downloads, and jobs. Schema auto-created on startup.

Design Decisions

Intentional constraints, not limitations

Every major decision in PokoDler was deliberate. Here's the reasoning behind the choices that might look unusual at first glance.

Decision 01

Why no npm or frontend build step?

The frontend is intentionally zero-toolchain. Static HTML, CSS, and vanilla JS served directly by FastAPI. No bundler, no transpiler, no node_modules.

This is a deliberate constraint that keeps the project deployable and understandable without a separate frontend environment. The UI's only job is to trigger the pipeline — it doesn't need a framework for that.

Decision 02

Why two Spotify auth strategies?

The Spotify API restricts editorial playlists behind OAuth scopes that aren't always available in a personal developer app. The sp_dc cookie flow was added as a pragmatic fallback for cases where OAuth doesn't cover the target content.

Supporting both means the tool works across more real-world situations — personal playlists via OAuth, editorial and regional content via the fallback.

Decision 03

Why semaphore-based concurrency, not a job queue?

Unbounded parallel downloads will saturate disk I/O and network bandwidth quickly. A full job queue (Celery, RQ) would add infrastructure overhead for a local tool.

A configurable asyncio semaphore cap achieves the same stability guarantee — bounded concurrency, graceful degradation, restartable partial runs — with zero additional dependencies or services to run.

Decision 04

Why PostgreSQL for a local-only tool?

Download history, job state, and Spotify mirror records need to survive restarts and be queryable. A flat file or SQLite would have worked for simple history, but PostgreSQL gives proper job tracking, progress upserts, and storage stats with almost no overhead for a local setup.

The bigger reason: it keeps the project consistent with the rest of the portfolio, where PostgreSQL is the operational spine across all data products.
